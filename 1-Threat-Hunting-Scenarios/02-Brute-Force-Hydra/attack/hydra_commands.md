Hydra Web Login Brute Force Attack Documentation
================================================

## Attack Name

Web Login Brute Force Against DVWA

---

## Attack Objective

The purpose of this exercise is to simulate an automated brute force attack
against the DVWA (Damn Vulnerable Web Application) login page using Hydra.

The attack generates repeated HTTP POST authentication requests that are later
collected by Apache Access Logs, forwarded into Splunk Enterprise, and used to
validate custom detection rules, automated alerting, and SOC investigation
workflows.

This attack was executed in a controlled SOC Home Lab environment for defensive
security training and detection engineering practice.

## Attack Prerequisites

Before executing the attack, the following conditions must be met:

• DVWA must be accessible from the attacker machine.

• Apache logging must be enabled.

• Splunk must be ingesting Apache Access Logs.

• A valid username or a username list must be available.

• A password wordlist must be prepared.

---

## Target Information

Example Target URL

http://192.168.xxx.xxx/dvwa/login.php

Hydra communicates directly with the login endpoint by repeatedly submitting
HTTP POST authentication requests using different password combinations until
the wordlist is exhausted or valid credentials are discovered.

---

## Hydra Command

hydra -l admin -P passwords.txt 192.168.xxx.xxx http-post-form "/dvwa/login.php:username=^USER^&password=^PASS^&Login=Login:F=Login failed"

---

## Command Breakdown

-l admin

Specifies a single username for authentication attempts.

Instead of testing multiple usernames, Hydra repeatedly attempts different
passwords for the account named "admin".

---

-P passwords.txt

Loads a password dictionary from the specified file.

Hydra reads the file line by line and submits every password against the target
authentication page.

---

192.168.xxx.xxx

Specifies the target web server hosting DVWA.

---

http-post-form

Selects Hydra's HTTP POST module.

Unlike FTP or SSH attacks, this module is designed specifically for web login
forms that submit credentials using HTTP POST requests.

---

/dvwa/login.php

The login endpoint responsible for processing user authentication.

Every password attempt is submitted to this page.

---

username=^USER^

Hydra automatically replaces the ^USER^ placeholder with the username provided
through the command line.

---

password=^PASS^

Hydra automatically replaces the ^PASS^ placeholder with each password read
from the supplied wordlist.

---

Login=Login

Represents the value of the HTML submit button required by the DVWA login form.

Without including this parameter, the request may not accurately emulate a real
user login attempt.

---

F=Login failed

Defines the failure condition.

Hydra examines the server response after each login attempt.

If the response contains the text "Login failed", Hydra considers the attempt
unsuccessful and continues testing the next password.

If the failure string is absent, Hydra assumes authentication was successful.

---

## Attack Workflow

Hydra starts by reading the username and password list.

↓

HTTP POST requests are generated automatically.

↓

Apache records every authentication request.

↓

Splunk Universal Forwarder collects Apache Access Logs.

↓

Logs are indexed by Splunk Enterprise.

↓

Custom SPL detection identifies excessive login attempts.

↓

A scheduled alert is generated.

↓

An email notification is sent.

↓

The analyst investigates the activity using the Detection and Investigation
Dashboards.

---

## Expected Indicators of Compromise (IOCs)

The attack generates several observable indicators:

• High volume of HTTP POST requests.

• Multiple requests targeting /dvwa/login.php.

• Repeated authentication failures.

• Same source IP generating consecutive requests.

• Automated User-Agent values.

• Increased authentication frequency within a short time window.

These indicators provide sufficient evidence for brute force detection within
Splunk.

---

## Expected Log Evidence

Apache Access Logs record information such as:

• Timestamp

• Source IP Address

• HTTP Method

• Requested URI

• HTTP Status Code

• User-Agent

These events become the primary telemetry source used by the detection rule.
