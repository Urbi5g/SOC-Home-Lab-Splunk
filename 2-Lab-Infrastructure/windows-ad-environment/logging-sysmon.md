# Windows Server Logging and Sysmon

## 1. Overview

The Windows Server component provides Active Directory Domain Services (AD DS) and domain infrastructure for the SOC home lab. Security events from the server can be used to investigate authentication activity, account changes, Kerberos requests, and other security-relevant behavior.

## 2. Lab Configuration

| Setting | Value |
|---|---|
| Hostname | `Ad-DC` |
| Fully Qualified Domain Name | `Ad-DC.soclab.local` |
| IP Address | `192.168.50.10` |
| Active Directory Domain | `soclab.local` |
| SIEM | Splunk Enterprise |
| Splunk Server | `192.168.50.2` |
| Relevant Windows Event | Security Event ID `4769` |

These values describe the current documented lab configuration. Confirm the server's installed components and active forwarding configuration before treating them as verified deployment status.

## 3. Logging Sources

### Windows Security Event Log

The Security log is useful for investigating:

- Kerberos service-ticket requests (Event ID 4769).
- Account authentication activity.
- Account and group changes.
- Other security events generated by Windows auditing policies.

Event availability depends on the configured audit policies and the activity performed in the lab.

### Sysmon

Sysmon provides detailed endpoint telemetry that may include:

- Process creation (Event ID 1).
- File creation (Event ID 11).
- Network connections (Event ID 3, when enabled by the configuration).
- DNS queries (Event ID 22, when enabled by the configuration).

The actual events collected depend on the installed Sysmon version and active configuration. Do not assume every event type is enabled.

## 4. Validation

Run the following commands in an elevated PowerShell session on the Windows Server.

Check the operating system and computer identity:

```powershell
hostname
Get-CimInstance Win32_OperatingSystem |
    Select-Object Caption, Version, BuildNumber

Get-CimInstance Win32_ComputerSystem |
    Select-Object Name, Domain, PartOfDomain
```

Check whether Sysmon is installed and running:

```powershell
Get-Service Sysmon64 -ErrorAction SilentlyContinue
Get-Service Sysmon -ErrorAction SilentlyContinue
```

Check the Sysmon configuration:

```powershell
sysmon64.exe -c
```

If the executable is not available through `PATH`, run it using its actual installation path.

Check recent Security events:

```powershell
Get-WinEvent -FilterHashtable @{
    LogName = 'Security'
    Id      = 4769
} -MaxEvents 10
```

Check recent Sysmon process-creation events:

```powershell
Get-WinEvent -FilterHashtable @{
    LogName = 'Microsoft-Windows-Sysmon/Operational'
    Id      = 1
} -MaxEvents 10
```

## 5. Splunk Verification

After configuring event forwarding, validate ingestion using the actual index and sourcetype configured for the server.

Example search:

```spl
index=wineventlog sourcetype=XmlWinEventLog
| stats count by host source sourcetype
| sort - count
```

To investigate Kerberos service-ticket requests:

```spl
index=wineventlog sourcetype=XmlWinEventLog EventCode=4769
| table _time host TargetUserName ServiceName TicketEncryptionType IpAddress
| sort - _time
```

A successful local query does not by itself prove that the events reached Splunk. Verify the results in Splunk and confirm the originating host.

## 6. Security Considerations

- Collect only the event categories required for the lab.
- Keep timestamps consistent across lab systems.
- Protect exported logs and screenshots from exposing credentials or sensitive information.
- Record the Sysmon configuration version and any changes made.
- Treat RC4-encrypted Kerberos tickets as an investigation signal, not proof of Kerberoasting by themselves.
